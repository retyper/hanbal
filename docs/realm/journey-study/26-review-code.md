## 0. 먼저: 세 안이 모두 틀리게 아는 사실 셋 (코드 확인)

**0-1. 「종류 등장 시각 표」는 없다. 있는 것은 5계단 tier 표다.** 21 은 `spawnMob` 안의 시각 표를 못 열었다고 쓰고, 23 은 「원거리 첫 등장 시각을 params 에서 확인 후」라고 쓴다. 실제는 `spawnMob`(haebi.ts:831) 이 `ST[stage].tiers[tierOf(s)]`(params.ts HAEBI_STAGES) 에서 두 종류를 뽑고, `tierOf = floor(t / bossTime × 5)`(haebi.ts:401) 다. 숲은 0~228초 `[club, dog]` · 228~456 `[runner, dog]` · 456~684 `[shield, berserker]` · 684~ `[berserker, archer]` · 912~ `[iron, firearcher]`. 시각 단위가 아니라 **판 길이의 5분의 1 계단**이고, 계단마다 `random(s) < share` 로 둘 중 하나를 고른다. 그래서 21 의 「1:00 dog 떼 · 2:00 archer 둘 · 3:30 shield 줄 · 4:30 runner」는 표 한 칸을 고치는 일이 아니라 **tier 구조를 시각 구조로 바꾸는 일**이다. 게다가 dog 는 이미 0계단에 있다(「1:00 에 dog 첫 등장」이 아님).

**0-2. 원거리를 앞 5분에 넣는 것은 지금 시험이 막는다.** `tests/raid-pacing.test.ts` 의 「50-1 모든 스테이지 전반 자연 스폰은 근접만」은 모든 스테이지에서 bossTime 의 0~49.9% 구간에 자연 스폰 원거리(archer · slinger · firearcher · hunter · torch · shaman)가 하나라도 있으면 실패한다 [확인]. 21(archer 2:00) · 23(B4 원거리 첫 등장 60~90초)은 이 「빨강 조건」을 정면으로 뒤집는다. 이 조건은 형의 11-15 「가만히 있어도 깬다」와 50-1 작업에서 나온 것이라, 뒤집으려면 형 말이 필요하고 시험도 같이 고쳐야 한다. 안들은 이 시험을 언급하지 않았다.

**0-3. 정예·두목이 설치물을 못 무는 까닭은 `m` 이 null 이어서가 아니다.** 23 은 「1920 줄이 `s.build && m` 이라 정예가 빠진다 → 정예도 들임」이라 쓴다. 실제로 스테이지 판의 정예·두목은 `initChampion`(champion.ts:26-33) 이 `e.champion` 을 달고, haebi.ts 의 `if (e.champion) { ... stepChampion(...); continue }` 가 설치물 줄(1931) **앞에서** 빠져나간다 [확인]. 조건 한 줄(`m` 을 넓힘)로는 안 되고, 정예 쪽(`stepChampion` 흐름: enter · 걷기 · 돌진 · 내려찍기)에 「설치물에 막혔을 때 문다」를 새로 넣어야 한다. 또 `(m.hit ?? 1)` 은 m 이 null 이면 바로 TypeError 다(`m?.hit` 로 고쳐야 함). 정예는 `pushOutOfBuild`(haebi.ts 1950대 · giant 아닌 모두)에 밀려 벽 앞에 서서 계속 밀리기만 하므로, 물지 않으면 벽 앞에 멈춰 선다.

## 1. 21 안: 재미와 중독 고리

### 1-1. 이대로 지으면 망하는 까닭

1. **`hasHp` 를 여덟으로 넓히면 항아리·솟대·봉수대·우물이 지어지자마자 무너진다.** `buildHp`(build.ts)는 망루·목책·장승·포차 외에는 0 을 돌려주고, `placeBuild`(haebi.ts:1634) 가 `max = buildHp(...) * threat` 로 `hp = 0` 을 넣는다. `buildStep`(haebi.ts:1769-1771) 은 `hasHp` 인 설치물의 `hp <= 0` 을 보면 곧바로 `down = rebuildOf(kind)` 로 눕힌다. 즉 체력 표(`buildHp`) · 재건 표(`rebuildOf` — 마지막 `: B2.catapult.rebuild` 로 떨어지는 삼항) · 단계 오르기(`buildPicked` haebi.ts:1641) · 눈금(fx-build.ts:64-70 의 hp 띠·재건 호)을 **같이** 넓혀야 한다. 21 은 `rebuildOf` 에 넷 추가를 말하지만 `buildHp` 는 말하지 않는다. 한 줄 고침이 아니다 [확인].
2. **누운(무너진) 설치물이 효과를 계속 낸다.** `standing()` 은 `down<=0 && (!hasHp || hp>0)` 로 쓰이는데, 우물 치유(build2Step · haebi.ts:1766-1771 근처 `for (const it of b.items) { if (it.kind !== 'well') continue ...}`)와 솟대 느려짐(`mobSlow` haebi.ts:1684)과 항아리 기세 보너스(`jarBonusAt` build.ts, 항아리 둘레 판정)는 **`standing` 을 안 본다** [확인]. 지금은 이 넷이 무적이라 늘 서 있어서 드러나지 않을 뿐이다. 체력을 주면 잔해가 된 우물이 계속 치유하고, 잔해가 된 솟대가 계속 느리게 하고, 잔해가 된 항아리가 계속 기세를 준다. 21 의 「부서지면 쿨이 멈추고 재건 초가 돈다」는 코드와 반대다. 우물 쿨은 `it.cd = max(0, it.cd - dt)` 가 `down` 중에도 돈다. 이 세 곳에 `standing` 검사를 먼저 넣어야 하고, 그것은 haebi.ts 한복판이다.
3. **기존 시험이 「무적」을 못 박아 두었다.** `tests/raid-build.test.ts:112`(항아리 `hp===0 && max===0`) · `:139`(항아리 무적) · `tests/raid-build2.test.ts:81`(솟대 무적) · `:104`(봉수대 `hp===0`)가 있다 [확인]. 체력을 새 규칙 태그(예 `75-WALL`)로 켜는 판에서만 주고, 옛 판(태그 없음)은 무적 그대로 두어야 이 넷이 산다. 21 은 3-2 에서 위험 값에만 옛 기록 처리를 쓰고, **체력 규칙 자체에는 태그를 안 적었다**. 태그 없이 고치면 옛 기록 재생이 어긋난다(아래 4절).
4. **초반 곡선을 params 값만 고치면 옛 판 기록이 전부 다른 판이 된다.** 생성 속도는 `C.spawnEarly/spawnMid/spawnLate/spawnFeast`(params.ts:309)로 바로 `rate`(haebi.ts:1881) 를 만든다. 규칙 태그가 없다. 값을 바꾸면 `replayRaid`(runlog.ts) 가 형의 11-22 이전 기록을 새 곡선으로 돌려 **입력·고르기는 그대로인데 적이 다르게 나온다**. `tools/raid-records.ts` · `src/records-main.ts` 가 이 재생을 쓴다. 이 저장소의 관행은 이 상황마다 규칙 태그를 하나 더하는 것이다(`72-BOSSHIT` · `74-BUFF` · `73-PHANTOM`). 21 은 곡선에 태그를 말하지 않는다. 또 `trial` 모드(본편 각성 시련)도 같은 `C.spawn*` 를 쓰고 `raid-pacing.test.ts` 의 「trial/vanguard 전체 상태는 변경 전 65초 결정론 기준과 같다」 해시(`ade44bf9…`)가 이것을 못 박고 있어서, 전역 값을 고치면 이 시험이 깨진다 [확인].
5. **(c) 「원거리는 장수가 설치물 반경 안에 있으면 설치물이 아니라 장수를 먼저 겨눈다」는 지금 코드에 일이 없다.** 원거리 잡졸은 처음부터 설치물을 겨누지 않고 장수(`s.x, s.y`)만 겨눈다(haebi.ts archer · slinger · firearcher 가지). 새로 만들 것은 「설치물을 겨누는 원거리」이고, 그것이 있어야 「장수를 먼저」가 의미가 생긴다. 새 규칙이므로 동결과 충돌한다. 21 의 (c) 는 빼는 것이 맞다.
6. **`loadMeta` 는 모르는 필드를 지운다.** 21 의 `riskOpen` · `heroRisk` 를 「`fresh()` 한 줄」이라 했지만, `loadMeta`(meta.ts:67-72) 는 `{ gold, spent, shop, cleared, best, runs, heroes, jackpots }` 를 **하나씩 골라** 새 객체를 만든다 [확인]. 새 필드는 `loadMeta` · `RaidMeta` · `cleanX` · `saveMeta` 흐름 전체에 더해야 하고, 안 그러면 저장 직후 다음 `loadMeta` 에서 사라진다. 이것은 험·위험을 출시 뒤로 미루는 쪽이라 지금은 급하지 않지만, 「옛 저장 이주 0」이라는 주장은 틀렸다.

### 1-4. 결정론 · 옛 기록 · 옛 저장 위험과 막는 법

- 위험(곡선): 태그 없는 params 수정은 모든 옛 재생을 바꾼다. **막는 법**: `76-PACE` 같은 태그를 `HaebiOpts` 에 더하고 `rate` 식(haebi.ts:1881) 한 곳에서 `s.pace ? 새 곡선 : 옛 곡선` 으로 가른다. 옛 곡선 상수는 `HAEBI_RUN` 에 그대로 두고 새 곡선은 별도 객체로. `createHaebi` 에 `if (opts.paceRules === PACE_RULES && mode === 'stage') s.pace = true`(BOSSHIT 와 같은 모양).
- 위험(체력): 1-1 ①~③. **막는 법**: 위 태그를 `75-WALL` 로 나누고 `hasHp`/`buildHp`/`rebuildOf` 를 `(kind, wall: boolean)` 꼴로 만들거나, 판이 `s.build.wall = true` 를 들고 읽는다(`s.build.v2` 가 이미 같은 방식). `standing` 도 같은 곳에서 가른다. 옛 판은 `wall` 이 없어 무적 그대로라 시험 4개가 그대로 산다.
- 위험(저장): 1-1 ⑥. 험·위험을 출시 뒤로 미룬 판단은 맞다.
- 규칙 태그를 하나 더할 때 **고쳐야 하는 곳 6곳**(BUFF 를 보고 센 것): `HaebiOpts` 타입(haebi.ts:283, 한 줄이 4KB) · 규칙 상수 · `createHaebi` 분기 · `raid-main.ts:130 runOpts` · `haebi-review.ts` 의 `createHaebi` 호출 · `tools/raid-stage-balance.ts stageToolOpts`(위치 인수 불리언이 이미 열다섯 개) · (`raid-well-probe.ts`). 오늘 밤 74-BUFF 일꾼이 이 여섯 줄을 지금 고치는 중이다 [확인: git status 가 이 파일들을 modified 로 보임].

### 1-5. 점수: **5.5 / 10**
읽을거리(근거 인용)는 가장 성실하지만, 규칙 태그가 빠졌고(곡선·체력), 시험이 못 박은 것(50-1 · 무적)을 모르고 있으며, 「분마다 하나」 표가 코드에 없는 구조를 전제한다. 험·위험을 출시 뒤로 미룬 판단과 「각성 문은 목책 한 판 유지」는 코드 쪽에서도 옳다.

## 2. 22 안: 장수와 이야기

### 2-1. 이대로 지으면 망하는 까닭
