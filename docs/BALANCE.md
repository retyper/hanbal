# 밸런스 기록

`npm run balance` 출력만이 근거다. 감으로 적지 않는다.
값을 바꿀 때마다 **날짜 / 무엇을 / 왜 / 측정값**을 표에 추가한다.

```
npm run balance                      기본 (40판 × 봇 3종 + 별·보상 + 화살 교차표)
npm run balance -- --cross=0         교차표 끄기 (빠르게 난이도만)
npm run balance -- --arrow=burst     드래프트 화살을 하나로 고정해 전 판을 돌린다
npm run balance -- --crossbot=expert 교차표를 숙련 봇으로
npm run balance -- --floor=1         보유 화살이 바닥난 사람이 겪는 판
npm run balance -- --preview=1       미저작 메커닉 프리뷰
npm run balance -- --campaign=0      해금 페이싱 캠페인 끄기 (기본 12명 × 봇 3종)
npm run balance -- --real=0          저작 원본(과녁만)으로 돌린다 — 기본은 플레이어가 받는 실제 판(보스·적 전환)
npm run balance -- --zero=1          스탯 전부 0 (성장 안 한 사람)  · --stats=str:8,stamina:3 지정
npm run balance -- --from=11 --to=20 캠페인 구간만

npm run probe                        배선 프로브 (부팅 전체 경로 + 화살 6종 비교)
```

---

> **칠십팔국(나라) 쪽 숫자는 `docs/realm/FLOW.md` "엔진에 들어간 것"의 봇 대전 표에 있다** (2026-10-18, `tools/realm-sim.ts --as all`).
> 이 문서의 나머지는 활터(기존 신궁)의 밸런스다.

## 0. 지금의 난이도 모델 (2026-08-23 떨림 재설계 이후)

> 이 절은 **옛 서술을 통째로 대체한다.** 예전 이 문서는 "떨림 위상을 읽고 최소점에 놓는 것이
> 실력"이라는 전제 위에 쓰여 있었다. 그 전제는 더 이상 참이 아니다.

### 무엇이 바뀌었나

사용자 피드백: *"떨림이 당기자마자 생기는 게 아니라 빨간 바 넘어가면 떨리게 해야겠어.
일반적으로 이렇게 유저가 쏘는대로 안 맞으면 화날 거 같다."*

그래서 정확도 모델을 통째로 바꿨다.

- `P.stamina.steadyZone`(0.55) = **빨간 바의 위치.** 최대 스태미나의 55% 지점.
- 스태미나가 그 위에 있는 동안이 **안전 구간**이다:
  떨림 0 · 발사 난수 오차 0 · **조준한 그 자리에 정확히 맞는다.**
- 아래로 내려가면 `ArcherState.strain`(0..1)이 자라고 떨림과 오차가 전부 여기 비례한다.
  `strain = (redAt − stamina) / redAt`.

**안전 구간의 폭 (실측, `stepArcher` 프로브)**

| 스탯 | 만작 도달 | 빨간 바 도달 | 안전 구간(만작 후) | 붕괴 |
|---|---|---|---|---|
| STAMINA 0 | 0.383s | 2.025s | **1.64s** | 4.32s |
| STAMINA 10 | 0.383s | 2.867s | **2.48s** | 6.19s |
| STAMINA 25 | 0.383s | 3.933s | **3.55s** | 8.57s |

STAMINA가 안전 구간을 넓힌다 — 성장 체감 지점이다.

**STR 축은 반대로 간다** (실측, 같은 프로브 · STAMINA 0 고정)

| 스탯 | maxDraw | 만작 도달 | 만작 소모 | 빨간 바 도달 | 안전 구간(만작 후) |
|---|---|---|---|---|---|
| STR 0 | 0.720 | 0.38s | 24.0/s | 2.02s | **1.64s** |
| STR 7 | 0.860 | 0.34s | 30.8/s | 1.59s | **1.25s** |
| STR 14 (진짜 만작) | 1.000 | 0.31s | 38.0/s | 1.30s | **0.99s** |

소모가 `draw^1.4`인데 `staminaMax`는 그대로라 **STR을 올리면 안전 구간이 40% 줄어든다.**
의도된 긴장이다(진짜 만작은 더 힘든 게 맞다) — 다만 숨기면 안 된다. 성장 화면의 지구력 문장이
`progression.safeSeconds()`로 이 값을 말하므로, STR을 올리는 순간 그 줄의 숫자가 눈앞에서 내려간다.

**호흡정지는 안전 구간을 태워 쓴다** — 소모가 ×2.6이라 STR 0에서 1.64s → **0.49s**,
STR 14에서 0.99s → **0.28s**. HUD의 눈금·숨쉬기가 실소모율(`drainNow`)을 쓰는 이유다.

### 클리어 조건이 바뀌었다 (2026-08-23)

**클리어 = 과녁을 다 없애는 것.** 점수가 아니다 (`sim/world.ts` evaluateEnd).
점수는 이제 **보상의 크기**이고, `StageDef.targetScore`는 별 2개의 기준선으로만 쓰인다.

이 변경이 밸런스에 만든 새 실패 모드가 하나 있다: **화살이 모자라 못 깨는 판.**
예전엔 점수만 채우면 과녁을 남겨두고도 넘어갔으므로 이 상태가 존재할 수 없었다.
그래서 시뮬이 실패를 두 갈래(화살 소진 / 시간 초과)로 나눠 세고, 요약에 `화살이 모자라 못 깬 판`을 찍는다.

### 난이도의 축

| | 옛 모델 | 새 모델 |
|---|---|---|
| 실력이란 | 떨림 위상을 읽고 최소점에 놓기 | **조준 정확도** + **안전 구간 안에 놓는 규율** |
| 난이도를 만드는 법 | 각크기 + 여벌 화살 | 각크기 + 여벌 화살 + **메커닉**(연쇄·이동·바람·관통) |
| 난이도를 만들면 **안 되는** 법 | — | `releaseScatter`·`baseAmp`·`steadyZone`을 키우기 |

마지막 줄이 핵심이다. **난수를 키워 어렵게 만드는 것은 금지다.**
그건 사용자가 방금 고치라고 한 문제("쏘는 대로 안 맞는다")를 그대로 되돌리는 짓이다.

**드래프트도 난이도 장치가 아니다.** 화살 선택은 판을 어렵게 만드는 게 아니라
**다른 판으로 만드는** 장치다 (docs/HOOK.md 1장). 화살로 클리어율을 조율하려 들면
"약한 화살을 뽑으면 진다"가 되어 3택이 벌칙이 된다.

### 각크기 곡선

반경은 손으로 적지 않는다. `stages.ts`의 `hFor(n)`이 정한다 —
1판 h=0.056(1280px 화면에서 반경 약 72px) → 40판 h=0.012(약 15px)의 지수 곡선.
h를 그 아래로 내리면 "조준 실력"이 아니라 "안 보이는 것 맞히기"가 된다.

## 1. 목표 수치

### 1-1. 난이도 (이번 작업에서 **바꾸지 않았다**)

| 지표 | 목표 | 현재 (2026-08-23, 200판/조합) |
|---|---|---|
| 1~10판 average 봇 클리어율 | 95~100% | **100.0%** ✅ |
| 11~25판 average 봇 클리어율 | 90~100% | 84.5%(3-4) 외 전부 99.5~100% ⚠ |
| 26~40판 average 봇 클리어율 | 80~95% | 대부분 **100%** — 목표 상단 초과 ⚠ |
| novice~expert 클리어율 격차 (≤40판) | 0~25%p | 38/40판 달성 (3-4 35.1%p · 4-8 36.9%p 초과) |
| 화살이 모자라 못 깨는 판 | 없어야 함 | **2판** (3-4 15.5% · 4-8 11.5%) ⚠ |
| 한 판 길이 (봇 기준) | 30초~1분 상당 | 1.4~14.2초 (사람은 한 발 4~6초라 6발이면 25~35초) ✅ |
| 25분 공부 후 플레이 가능 판 수 | ≥ 3판 | 3판 ✅ |

> **26~40판이 100%인 것을 "고쳤다"고 적지 않는다.** 이번 작업의 지시는 난이도를 올리지 않는
> 것이었고, 여기는 스테이지 담당의 영역이다. 계측기는 벗어난 사실만 기록한다.

### 1-2. 안전 구간 (떨림 모델 회귀 감시)

| 지표 | 목표 | 왜 |
|---|---|---|
| **안전 발의 릴리즈 각오차 RMS** | **정확히 0.000 mrad** | 이게 깨지면 sim 회귀다. 약속 자체가 무효 |
| expert의 안전 구간 안 발사 비율 | ≥ 90% | 규율이 숙련의 정의다 |
| average의 안전 구간 안 발사 비율 | 75~85% | "대개 안에, 가끔 넘긴다" |
| novice의 안전 구간 안 발사 비율 | ≤ 35% | "망설이다 넘긴다"가 초보의 정의다 |
| 안전 명중률 − 넘김 명중률 | > 0, 정확한 봇일수록 커야 함 | 아래 주의 참조 |
| novice 붕괴 발사 비율 | 5~20% | 붕괴가 실제 위협이어야 한다 |

> **격차의 크기에 대한 주의.** 이 격차는 물리적으로 `떨림 RMS / 조준 σ` 비에 묶여 있다.
> 넘김 발의 떨림 RMS는 strain 0.44에서 2.1 mrad, 붕괴 직전(0.69)에도 4.1 mrad가 상한이다.
> 반면 사람이 마우스로 겨누는 오차는 3.6~7.5 mrad다. 즉 넘겨도 총 오차는
> √(조준² + 떨림²)로 20~30%만 늘어난다. 절대 크기가 작은 건 정상이고,
> **순서(expert > average > novice)가 뒤집히면 그때가 회귀다.**

### 1-3. 별 분포 (docs/HOOK.md ★4 — 재도전의 이유) ★신규

| 지표 | 목표 | 왜 |
|---|---|---|
| average 봇 ★★ 이상 | ≥ 55% | 대체로 잘 나와야 별이 벌이 아니라 보상이 된다 |
| average 봇 **★★★** | **5~30%** | 너무 흔하면 다시 할 이유가 없고, 너무 희귀하면 시작 전에 포기한다 |
| ★ (별 1개)가 실제로 나오는가 | > 0% | 세 단계가 다 존재해야 별이 눈금이다 |
| ★★★인데 실제로 빗나간 발이 있던 판 | ≈ 0% | '무손실'이 무손실을 재고 있는가 |

### 1-4. 변동 보상 분산 (docs/HOOK.md ★3 — 운이 실력을 덮지 않는가) ★신규

| 지표 | 목표 | 왜 |
|---|---|---|
| 실력 순서 | exp > avg > nov | 뒤집히면 성장이 무의미해진다. **즉시 실패** |
| **효과크기 d** = (같은 판에서 exp−nov 평균) / (판 안 σ) | **≥ 1.0** | 한 판만 봐도 실력이 보인다. 0.5 미만이면 운이 실력을 덮는다 |
| 변동 보너스의 지분 (보너스 합 / 훈련치 합) | 10~20% | 기대감은 주되 결과를 정하지는 않는다 |

> **σ는 반드시 판 안에서 잰다.** 전 판을 한 통에 섞으면 "1-1은 원래 적게 주고 4-10은 원래
> 많이 준다"는 스테이지 차이가 통째로 운으로 계산되어, 어떤 보상 설계를 넣어도 d가 0.2로 나온다.
> 플레이어가 실제로 겪는 비교는 "같은 판을 초보가 하면 vs 숙련이 하면"이다.

### 1-5. 화살 드래프트 교차표 (docs/HOOK.md ★1 — 선택이 장식인가) ★신규

`npm run balance`가 화살 9종 × 62판을 돌려 세 가지를 판정한다.

| 판정 | 조건 | 뜻 |
|---|---|---|
| **미배선** | 화살을 바꿔도 결과가 완전히 같다 | 고른 게 sim에 도달하지 않았다 |
| **장식** | 70% 이상의 판에서 최고/최저 점수 비 < 1.10 | 골라도 판이 안 바뀐다 |
| **지배 전략** | 한 화살이 60% 이상의 판에서 1등 | 3택이 사실상 1택이다 |
| **통과** | 판마다 다른 화살이 1등이고 지배 전략이 없다 | 40판이 40판 × 화살이 됐다 |

화살은 `createWorld(stage, stats, arrow)`의 3번째 인자로 sim에 들어간다 (`World.arrowKind`·`World.fx`).

**점수 1등만 세면 안 된다.** 폭발·분열·사슬은 점수를 깎는 대신 판을 빨리 정리하는 화살이라
(딸려 죽은 과녁은 링 배수가 낮다) 점수 줄세우기에서 영원히 0등이다. 그래서 표는
**'화살 절약 1등'**(판당 평균 사용 화살이 가장 적은 화살)을 같이 센다. 그게 이 세 화살이
실제로 주는 것 — 여벌 화살과 무손실(★★★) — 이다.

### 1-6. 해금 페이싱 (docs/HOOK.md ★2 · GDD C3) ★신규

`npm run balance`의 캠페인 모드가 1판부터 순서대로 돌며 각 해금이 몇 판째에 열리는지 잰다.

| 지표 | 목표 | 왜 |
|---|---|---|
| 모든 화살 해금의 40판 안 달성률 | **100%** | 안 열리는 화살은 드래프트에 안 나온다 = 없는 화살이다 |
| 칭호 해금의 40판 안 달성률 | ≥ 50% | 늦어도 되지만 체념할 만큼 멀면 안 된다 |
| 열리는 판의 분포 | 40판에 고르게 | 언제 봐도 2~3칸이 손에 닿아야 한다 (HOOK ★2) |
| 별도의 그라인드 구간 | 없어야 함 | 갈아넣게 만들면 공부를 잡아먹는다 (C3) |

## 2. 봇 3종 (`tools/balance-sim.ts`)

봇은 World를 읽어 InputFrame을 만드는 함수일 뿐이다. World를 직접 건드리지 않는다.

### 조준 오차 (새 모델에서 실력의 주된 축)

| 봇 | 바닥 σ (rad) | 30m에서 | 화면(1200px) | 획득 σ | 수렴 τ | 초속 오판 |
|---|---|---|---|---|---|---|
| novice | 0.0075 | 22.5 cm | 9.0 px | 0.040 | 0.45s | +2.0% |
| average | 0.0050 | 15.0 cm | 6.0 px | 0.028 | 0.22s | +0.7% |
| expert | 0.0036 | 10.8 cm | 4.3 px | 0.020 | 0.08s | 0 |

- 만작까지가 0.37초다. τ가 그보다 크면 "당기는 동안 조준을 못 끝낸다"는 뜻이다.
- 마우스 1px ≈ 0.00083 rad. 이보다 정밀한 봇은 사람이 아니다 — 그게 σ의 하한이다.
- **novice/expert의 σ 비 2.08은 임의가 아니다.** 클리어율은 한 발 명중률의 가파른 함수라
  σ 비가 2.5를 넘으면 격차가 목표 상단을 반드시 넘는다.

### 릴리즈 규율 (두 번째 축)

| 봇 | 잡는 스태미나 | 평소 망설임 | 발작 | strainBail | 경고에 놓나 |
|---|---|---|---|---|---|
| novice | 85% | 만작 후 **0.4~3.8s** 균등 | — | 1.0 (인지 못함) | ✗ |
| average | 88% | 만작 후 0.15~0.85s | 18% 확률로 1.6~3.2s | 0.90 | ✓ |
| expert | 95% | 만작 후 0.03~0.14s | 4% 확률로 1.6~2.8s | 0.90 | ✓ |

- novice의 망설임 범위(최대 3.8s)는 붕괴 시각(약 3.4s)을 넘는다 — 그래서 12%가 붕괴다.
- expert의 발작 4%는 **측정을 위해 일부러 남겼다.** 0이면 "정확한 사람이 바를 넘기면
  얼마나 손해인가"를 잴 표본이 없다.
- 호흡정지는 세 봇 다 쓰지 않는다 (챕터 8의 학습 목표라 측정 대상이 어긋난다).

### 발사 대기 규칙 — 2026-08-23 추가

봇은 다음 발을 잡기 전에 두 가지를 기다린다.

1. **날아가는 화살** — 사람은 맞았는지 보고 다음을 정한다.
2. **낙하 중인 공중 과녁** ★신규 — 연쇄가 아직 진행 중이다.

2번이 없을 때의 실측 오염이 컸다. 낙하물은 아래 과녁을 쓸어버리므로, 안 기다리는 봇은
**몇 초 뒤 저절로 죽을 과녁**에 화살을 한 발 버린다. 그 손해는 빨리 쏘는 봇일수록 커서
챕터 2에서 **expert의 발당 명중률이 novice보다 20%p 낮게** 나왔고, 그 결과
안전/넘김 명중률 격차의 부호가 뒤집히고(expert −10.0%p) 보상의 실력 순서까지 깨졌다
(exp 17.96 < nov 18.64). 게임이 아니라 봇의 성급함을 재고 있었던 것이다.

수정 후 전부 제자리로 돌아왔다 (아래 §4 참조). **이 규칙을 지우면 그 오염이 그대로 돌아온다.**

### 한 발 명중률 회귀식

`p(h) ≈ erf(h / s)`, s = novice 0.0107 · average 0.0068 · expert 0.0049.
스테이지를 저작할 때 이 식으로 h를 역산하고 `npm run balance`로 확인한다.
(지금의 h 곡선은 이 식의 포화 구간이라 앞 40판에서 세 봇이 거의 갈리지 않는다 — 의도된 것이다.)

   **깨면 점수가 반드시 `targetScore` 이상**이었다 — 즉 ★★는 클리어의 다른 이름이었고 ★은
   구조적으로 불가능했다. 1.6배로 올리면 링 배수(최대 2배)와 연쇄가 얹혀야 닿는다.
   결과: ★ 0.0% → 3.0%, ★★ 5.5% → 51.8%. **세 단계가 다 존재한다.**
2. **무손실 판정을 `hits >= shots`에서 `misses === 0`으로 바꿨다.** 관통 살로 셋을 꿰뚫고 한 발을
   완전히 흘려도 `hits 3 ≥ shots 2`라 무손실이 되는 거짓 양성이 있었다(배선 전 오검출 0.4%,
   드래프트가 붙으면 커질 값). 지금은 `miss` 이벤트를 직접 센다 — 실측 오검출 **0.0%** (0/2124).

> **정정 (2026-08-24, sim-lens)**: 위의 "오검출 0.0%"는 한동안 **측정이 아니라 항등식**이었다.
> 시뮬이 `runStats.misses`를 `shots - hitShots`로 만들고 자가 점검도 같은 식을 봐서, 검사가
> 논리적으로 성립할 수 없었다. 지금은 시뮬이 게임(loop.ts)과 **같은 축**(miss 이벤트 수)으로
> 채점하고, 자가 점검은 **발 단위**(`hitShots < shots`)라는 다른 축으로 대조한다.
> 두 축을 실제로 맞대고 잰 값이 **0.0% (0/2276)** 이다.

**남은 문제: ★★★ 44.2%** (목표 5~30%). 원인은 보상식이 아니라 **난이도 정책**이다 —
앞 40판은 "여기서 실력을 가르지 않는다"가 방침이고(§0), average 봇의 발당 명중률이 95.6%라
5~7발 판에서 무손실이 자연스러운 기본값이 된다. 문턱을 더 조이려면 별을 손볼 게 아니라
난이도를 손봐야 하는데 그건 이번 작업의 범위 밖이다. **기록만 남긴다.**

읽는 법: **같은 판에서 보너스를 빼면 초보와 숙련의 훈련치 차이(1.34)가 판 안 흔들림(1.47)과

1.47 → 6.34로 **4.3배** 뛰어, 실력 신호가 통째로 잠긴다. 한 판만 놓고 보면
"잘 쏜 초보"가 "못 쏜 숙련"보다 훈련치를 더 버는 일이 흔하다.

원인은 보너스가 **곱셈**이라는 데 있다 (`bonus = subtotal × 1.5` 또는 `× 0.6`).
소계가 클수록 보너스도 커지므로 분산이 평균에 비례해 자란다.

**이번 작업에서는 안 고쳤다. 이유를 정확히 적어둔다.**

운을 완전히 끈 상태의 d가 **0.98**이다. 즉 보너스를 아무리 줄여도 **d는 0.93을 못 넘는다** —
이건 운의 문제가 아니라 **보상식이 실력을 덜 읽는** 문제다. 같은 판에서 초보와 숙련의
훈련치 차이가 1.57밖에 안 되는데, 그 이유는 앞 40판이 "여기서 실력을 가르지 않는다"는
난이도 정책(§0) 위에 있어 **초보도 거의 다 깨기 때문**이다. 깨는 것 자체가 안 갈리면
보상도 안 갈린다.

d를 1.0 위로 올리는 유일한 길은 **실력 항을 키우는 것**이다 (`SCORE_TRAIN 4` 인상 또는
`SCORE_RATIO_CAP 2.5` 인상). 그런데 그건 판당 훈련치를 통째로 부풀려 성장 곡선(GDD 4장,
진짜 만작까지 누적 167)을 다시 재야 하는 변경이고, 이번 지시("배선과 수리만")의 범위 밖이다.
**보너스의 곱셈 구조를 건드려도 해결되지 않는다는 사실**만 여기 확정해 둔다.

재실행 한 번으로 판정된다: `npm run balance -- --cross=0` → "효과크기 d".

**점수 1등만으로는 반쪽이라 '화살 절약 1등'을 새로 센다.** 폭발·분열·사슬은 점수를 **깎는** 대신

0등이라 "장식"으로 오독하게 된다. 실제로 얻는 건 여벌 화살과 무손실(★★★)이다 —
예: 2-5에서 사슬 살은 3발 → **1발**, 2-8에서 폭발 살은 4발 → **2발**.

**미리 적어둔 예측 대조** (§이전 판의 예측):
- `heavy`(scoreMul 2) 지배 전략 예측 → **맞았다.** 40/40 판에서 점수 1등이었다.
  점수 배수를 2.0으로 두면 **아무 효과도 발휘될 수 없는 판**(과녁이 서로 먼 판, 40판 중 26판)에서
  자동으로 1등이 된다. 관통을 떼도 29/40이라 크기 문제가 아니라 종류 문제다.
  → **`arrowkind.heavyScoreMul`을 1로 내렸다.** 무거운 살의 정체성은
  '가장 깊은 관통(손실 0.09) + 바람에 안 밀림(dragMul 0.6) + 느림(speedMul 0.72)'으로 옮겼다.
- `chain`(7.0m) → **너무 셌다.** 챕터 1의 과녁 간격이 4~6m라 한 발이 판 전체를 지웠다

- `burst`(2.2m) → 예측대로 연쇄 기둥에서만 작동한다. 다만 점수는 기본 살보다 **낮다**(위 참조).

### 계측기 자신의 숙제

5. **26~40판이 average 봇 100%다** (목표 80~95%). 이번 작업은 난이도를 올리지 않는 것이
   지시였으므로 기록만 해 둔다. 다만 봇 클리어율은 사람의 체감 난이도가 아니다 —
   봇은 각오차(mrad)로 조준하고 사람은 화면 픽셀로 조준한다. 40판이 전부 100%인 게
   "너무 쉽다"인지 "봇이 사람보다 잘한다"인지는 이 도구가 답할 수 없다.
   답하려면 **사람의 조준 오차를 픽셀 단위로 모델링한 봇**이 필요하다.
6. **캠페인 모드가 스탯을 성장시키지 않는다.** §4-6은 `assumedStats(progress)`를 그대로 쓴다.
   훈련치를 `spendTraining`으로 굴려 진짜 성장 곡선을 태우면 해금 판수가 조금 당겨질 것이다
   (스탯이 오르면 클리어가 빨라진다). 지금 값은 **보수적인 상한**으로 읽으면 된다.
7. **캠페인의 3택은 균등 선택이다.** 사람이 어떤 카드를 좋아하는지는 이 도구가 답할 수 없는
   질문이라 일부러 모델링하지 않았다. 즉 §4-6은 "아무거나 골라도 이만큼 열린다"는 하한이다.
8. **안전/넘김 명중률 격차가 앞 40판에서 의미를 잃었다.** 과녁이 커져 명중률이 96%로 포화했다.
   이 지표는 41판 이후(무한 모드)에서 다시 유효해진다. 그때까지는 **안전 발 오차 RMS 0.000 mrad**
   한 칸만 회귀 감시로 쓴다.
9. **난이도는 언제나 과녁 반경·거리·화살 수·메커닉으로 만든다.**
   `releaseScatter`·`baseAmp`·`steadyZone`으로 되돌리지 않는다. 드래프트로도 만들지 않는다.

## 7. 갈림길 2택 검증 (2026-08-26, balance-lens)

`npm run balance`는 forks.ts를 전혀 모른다 — `hasFork`/`applyFork`/`windTrainMul`을 import하는
파일이 `src/game` 안에 없다(grep 확인). 그래서 이번 검증은 `tools/balance-sim.ts`의 봇 모델
(BOTS·Bot 클래스·탄도 해)을 그대로 복사해 임시 스크립트를 짜고, 검증 후 삭제했다
(재구현하지 않고 복사한 이유: 물리가 미묘하게 어긋나면 게임이 아니라 스크립트를 재게 된다).
**계측기 자체에 `--fork=wind|dense` 같은 옵션이 없다는 것부터가 이번 숙제다.**

### 7-1. 바람골 — 위험이 거의 없는데 훈련치는 확정 +60%다 ✗

`windFloor=6`을 과녁 1~9판(챕터1, 원저작 STAGES·챕터2+ 전환 문제 없는 구간)에 강제로 걸고
바닥 지급(화살 보유 0) 조건에서 300회씩 비교했다.

| 판 | wind 0→6 클리어율 변화 (novice) | wind 0→6 클리어율 변화 (average) |
|---|---|---|
| 1-1~1-9 전부 | 100.0% → 100.0% (변화 없음) | 100.0% → 100.0% (변화 없음) |

각도 오차를 직접 재도 같다 — 3-1(거리 16m)에서 wind을 **0 → 30**(설계 최대 6의 5배)까지 올려도
목표 y 오차는 −0.002m → −0.001m로 **1cm 미만**, 과녁 반경(0.48m)의 1%가 안 된다.
바람이 "쏘는 대로 안 맞는" 축이 아니라 사실상 배경 연출에 가깝다 — `bow.windMul`·`arrow.drag`가
바람을 속도 항력으로만 반영해서, 이 게임의 짧은 비행시간(0.3~0.6s)에서는 각도 보정 없이도
(novice의 `windAware=0`, 즉 바람을 아예 무시하는 봇도) 클리어율이 흔들리지 않는다.

**여정 비교** (챕터1, 9판, 화살 회복 없이 이어 돌기, N=150, 세 봇 다 동일 패턴):

| 정책 | 클리어 9/9 | 화살소진 실패 | 훈련치 합 (9판) | 판당 |
|---|---|---|---|---|
| 바람골만 | 9.0 | 0.00 | **239.6~240.1** | 26.7 |
| 아무것도 안 고름(=미적용 기준선) | 9.0 | 0.00 | 151.5~151.6 | 16.8 |
| 밀집만 | 9.0 | 0.00~0.02 | 175.5~177.7 | 19.6 |

바람골 훈련치 배수는 실측으로도 정확히 **×1.58~1.60**(선언값 1.6과 일치, 클리어율 100%라
그대로 드러난다) — 근데 그 대가로 재는 클리어율 손실이 **0%p**다. `docs/BALANCE.md` §1-4가
이미 적어 둔 변동 보상의 기대 기여(+14.4%, 확률 4%/14%)와 비교하면, 확정적으로 매판
고를 수 있는 **+60%**는 그보다 4배 이상 크고 운이 아니라 선택이다. 실력 격차(§4-4, exp−nov
같은 판 평균 1.57)보다도 훨씬 크다. **판정: 위험/보상이 다른 축이 아니라 "보상만 있고 위험은
없는 축"이다.** 형이 설계 문서에 적은 "위험/보상이 서로 다른 축이어야 한다"(요구사항)를
현재 수치는 만족하지 못한다.

제안(수치만 — 실제 반영은 담당 판단):
- `windFloor`를 더 올리거나(6 → 12~15까지 올려도 위 표에 따르면 여전히 거의 안 아프다),
- 또는 `windTrainMul`을 클리어율 손실이 실제로 측정되는 지점까지 낮추거나,
- 근본적으로는 **바람의 드래그 계수 자체가 약하다**는 물리 쪽 문제라 sim-lens/feel-lens 검토가
  먼저 필요하다. 바람골 배수만 만지면 "약한 위험에 약한 보상"이 될 뿐 축이 두 개가 되지 않는다.

### 7-2. 밀집 — 화살 극단(0 또는 풍족)에서는 안전, 그 사이(가장 흔한 상황)에서는 아니다 △

> **폐기됨 (2026-08-31).** 아래 분석은 밀집이 살아 있던 시절의 기록이다. 밀집은 지금
> 게임에 없다 — 복제 방식이 과녁 겹침·지면 관통을 구조적으로 못 막았다(형의 신고).
> 갈림길은 여섯 장의 패로 다시 짰다: `src/game/forks.ts`. 새 카드들의 훈련치 배수
> (척후 ×1.2 · 단발 ×1.4)는 **아직 여기서 측정되지 않았다** — §7-1이 짚은 함정
> (봇 명중률 100%라 위험이 안 잡힌다)이 그대로 남아 있는 축이다.

`grantArrows(save, stage)`: `min = max(minArrows, stage.arrows − spareCut)`,
`granted = clamp(save.arrows, min, stage.arrows)`.

밀집이 `stage.arrows`를 `+denseExtra`(기본 2, 실제로는 복제 가능한 과녁 수에 막혀 1~2)만큼
올리면:

- **화살 보유고 0(바닥)** — `min`이 정확히 `denseExtra − spareCut`만큼만 움직인다.
  기본값이 `denseExtra == spareCut == 2`라 이 항이 **0으로 상쇄**되고, 바닥 지급량은
  밀집을 고르지 않았을 때와 **정확히 같다**(margin 불변, 실측 §다음 표). 이건 우연이 아니라
  두 노브가 같은 값이라서 생기는 결과다 — **문서화되지 않은 결합**이다.
- **화살 보유고가 풍족(≥ 새 stage.arrows)** — `granted`가 그대로 늘어난 목표치를 다 채워
  준다. 역시 안전.
- **그 중간 — 보유고가 딱 "원래 판 하나 치"만큼(가장 흔한, 막 이전 판을 여유 있게 깬 상태)**
  — `granted = min(have, stage.arrows)`가 **`have`에서 안 늘어난다.** 실측(그랜트 마진 =
  지급 화살 − 과녁 수):

  | 판 | 밀집 전 마진 (기준: have=base.arrows) | 밀집 후 마진 | Δ |
  |---|---|---|---|
  | 1-1 | 4 | 3 | **−1** |
  | 1-3 | 4 | 2 | **−2** |
  | 1-5~1-8 | 4 | 2 | **−2** |
  | 1-9 | 4 | 2 | **−2** |
  | 2-1 | 6 | 4 | **−2** |
  | 2-2 | 5 | 3 | **−2** |

  Δ는 항상 `−k`(실제로 복제된 과녁 수, 1~2)와 일치한다 — "보유고가 딱 맞을 때는 화살이
  과녁 수만큼 안 따라온다"는 게 정확한 수식이다. 다만 실측 클리어율로는(위 §7-1 표,
  바닥 지급·9판 전부) 밀집의 화살소진 실패가 **0.00~0.02**로 거의 안 보였다 —
  챕터1의 기본 마진 자체가 3~4로 넉넉해서 1~2를 깎여도 아직 벽에 안 닿는다.
  **판정: 지금 당장 챕터1에서 벽은 아니지만, 마진이 이미 빠듯한 판(§4-1의 3-4·4-8,
  마진 2.1~2.2)에서 밀집을 고르면 그 판은 실측 없이도 위험하다고 볼 수 있다** — 7-3에서
  왜 재확인을 못 했는지 적는다.

### 7-3. ★발견★ 계측기가 챕터2+를 다른 게임으로 재고 있다 (포크와 별개, 더 급함)

`tools/balance-sim.ts`의 `REAL_STAGES`는 `STAGES`(원저작, 변환 전)를 그대로 쓴다.
`playCampaign`도 `ALL_STAGES[stageIndex]`를 쓴다 — **둘 다 `getStage(i)`를 안 부른다.**
그런데 실제 게임(`game/loop.ts`)은 언제나 `getStage(stageIndex)`로 판을 얻고, `stages.ts`의
`getStage`는 11판째부터 `convertToFoes`를 걸어 **과녁을 전부 반격하는 적 궁수로 바꾼다**
(정적 1회 피격 과녁 → HP 있고 나를 쏘는 `archer`). 실측:

```
STAGES[11] (2-2, 미변환): arrows=6, targets=['aerial','static','static']
getStage(11) (2-2, 실제 게임):     arrows=8, targets=['archer','archer','archer']
```

즉 `docs/BALANCE.md`의 §4-1(40판 난이도 표)·§4-6(캠페인 해금)·§4-7(화살 바닥)에 있는
**2판~40판 전체 숫자는 챕터2+에서 실제로 배가 안 되는(반격 안 하는) 과녁을 잰 것**이다.
챕터1(1~10판)은 애초에 변환이 없어 멀쩡하다 — 이번 §7-1/7-2의 챕터1 수치는 이 문제와
무관하게 유효하다.

이게 밀집(밀집은 `getStage`가 준 실제 판에 적용됨, 클론 대상에서 'archer'를 안 뺀다 —
`forks.ts` 74행 필터가 `bonus`·`boss`·`charger`만 뺀다)에 갖는 의미: **챕터2+에서 밀집을 고르면
"과녁"이 아니라 "나에게 화살을 쏘는 적"을 복제한다.** 화살(탄약) 마진 계산은 위 §7-2와 같은
수식을 따르겠지만, 위험의 진짜 축은 화살이 아니라 **체력(w.hp)**일 수 있다 — 이건 이번
검증 범위 밖이다(계측기가 애초에 이 축을 안 쟀다).

**이건 밀집/바람골 밸런스 문제가 아니라 계측기 결함이라 별도로 적어 둔다.**
`REAL_STAGES`/`playCampaign`을 `STAGES[i]` 대신 `getStage(i)`로 바꾸면 챕터2+의 모든 §4
수치가 다시 재야 하는 값이 된다. balance-sim 담당에게 넘긴다 — 이번 포크 검증은 그 결함을
피해 **챕터1로 범위를 좁혀** 얻은 값만 신뢰할 수 있다.

### 7-4. 결론 요약

### 7-5. 조치 (2026-08-26)

`P.fork.windTrainMul`을 1.6 → **1.15**로 내렸다 (`src/tune/params.ts`, 근거는 노브 주석에

  만드는지는 이번 검증 범위 밖이다 (§7-3).

## 8. ★ 11판의 벽 — 시뮬이 그동안 존재하지 않는 판을 재고 있었다 (2026-09-02)

> 형: "여자친구가 해봤는데 11까지 가고 어려워서 안하겠대. 아마 강화하는걸 안해봤나봐."

### 8-1. 계측기의 결함

`REAL_STAGES`가 **저작 원본**(`STAGES`, 과녁만)을 돌렸다. 실제 플레이어가 받는 판은
`getStage()`가 내보내는 것 — 10판마다 보스, **11판부터 전부 사수**(체력 70, 6초마다 나를 쏜다).
그래서 이 문서 §4의 11판 이후 모든 줄은 게임에 없는 판의 값이었다. 예: 2-2는 "100% · 3발"로
적혀 있었는데 실제 2-2는 아래와 같다.

이제 기본이 실제 판이다 (`--real=0`으로만 옛 원본). 표에 `death`(적에게 쓰러진 비율) 열이 생겼다.

### 8-2. 실측 — 경사 **전** (seed 20260823 · 26판/조합 · 실제 판)


원인은 피해식이다 (`sim/target.ts damageOf`): **피해 = 40 × (착탄 속도/60)²**.
근력 0의 만작(0.72)은 초속 38 → 착탄 ~33 → 피해 **12**. 사수 체력 70에 **여섯 발**.
근력 8은 25(세 발), 근력 14(진짜 만작)는 36(두 발). 다른 세 스탯은 이 수를 안 바꾼다.
즉 11판은 "성장을 안 한 사람이 처음 부딛히는 벽"이었고, 형의 짐작이 정확했다.
(봇은 몸통 중심을 노린다 — 사람은 헤드샷으로 일부 만회하지만, 처음 하는 사람은 못 한다.)

## 9. 경제 — 훈련치 수입과 소비처 (2026-09-02, 저녁에 전면 개정)

> 형: "다 너무 싼 거 아냐? 컨텐트 소모시간이 너무 빨라버리는 거 같은데" · "내가 한 10분 플레이하면 1000 모은단 말이야."

### 9-1. 계측기 — `node --experimental-strip-types tools/probe-economy.ts [--old=1]`

수입은 실제 채점기(`gradeRun`)에 실제 판을 넣어 잰다. 두 사람:
초보(깨되 한 발 흘림 · 점수 = 기준선 · 판에 25초) · 숙련(무손실 · 정중앙 둘 · 점수 상한 · 판에 12초).

```
초보  판당 10.3  분당  25   10분  247
숙련  판당 25.3  분당 126   10분 1263   ← 형의 "10분에 1000"과 맞는다
```

### 9-2. 옛 값 (오전) — 왜 "다 너무 싸다"가 맞았나

```
                       총액    숙련이 다 사는 데    초보
근력 14                 167         1분              7분
4스탯 14 + 주활 개조    776         6분             31분    ← 핵심 영구 세트
전부 (4스탯 30·활 다섯) 4632        37분            187분
부적 하나                 9      0.4판 수입       0.9판 수입
```
비용식이 제곱(quadDiv 16)뿐이라 14레벨이 25였다. 판 하나 수입(25)으로 후반 레벨 하나를 산다 — 곡선이 없었다.

### 9-3. 새 값 — 앞은 그대로 싸게, 뒤만 가파르게

| 무엇 | 전 | 후 |
|---|---|---|
| 스탯 비용식 | 2 + l + l²/16 | 2 + l + l²/6 + **l³/14** (L5 19 · L10 99 · L14 244 · L20 659 · L29 1913) |
| 개조 3단 | 6 · 12 · 18 | **60 · 220 · 540** (60 + 80l + 80l²) |
| 부적 | 8~12 | **35~60** |
| 화살 한 발 | 4 → 7 → 10 | **12 → 24 → 36** |
| 살 가게 | 3·4·5·7 | **10·15·20·30** |

```
                       총액    숙련         초보
근력 0→8               117      1분         5분   (초보 11판 도착 시 누적 102 → 근력 7)
근력 14                837      7분        34분
4스탯 14              3344     26분       135분
주활 개조 전부        2460     19분       100분
★ 핵심 영구 세트      5804     46분       235분 (≈4시간)
전부                 73952    585분 (≈10h) 2993분 (≈50h)
부적 하나               48    1.9판 수입    4.6판 수입
화살 셋                 72    2.9판 수입    7.0판 수입
```

읽는 법:
- **첫 여정은 안 건드렸다.** 초보의 11판 도착 시 근력 7 (전 11) — §8의 "근력 8이면 11~19판이 열린다"에
  거의 닿고, 체크포인트에서 한 바퀴 더 벌면 넘는다. 여자친구 시나리오는 그대로 성립한다.
- 숙련자의 지갑은 이제 **한 시간 남짓** 열려 있고, 그 뒤 스탯 20+·다른 활 개조라는 열 시간짜리
  꼬리가 남는다. 스탯 20 이후는 수확체감(diminishAt 20)이라 꼬리의 가치는 낮다 — 그건 의도다.
- 부적은 이제 여정 수입의 15~30%다. "이번엔 지니고 갈까"가 비로소 결정이다.
- **숙련의 수입 자체는 안 줄였다** — 빨리 깨는 것이 보상인 건 MEGAHIT §1의 결정이다. 그래도 분당 126은
  초보의 5배라, 숙련자가 모든 값을 초보의 1/5 시간에 산다는 사실은 남는다. 값으로 못 고치는 격차다.

금관 헤드샷 실제 성공률 · 화살 한 발을 실제로 사는 빈도 · "10분에 1000"이 새 값에서 어떻게 느껴지는가.

  - 첫 화면(지붕을 보기 전)에서 건너뛰기 = 안 쏜 것과 **똑같다** (배수 1). 아무것도 안 봤으니 깎을 까닭이 없다.
  - 진짜 지붕에 들어가 첫 살을 쏘기 **전에** 건너뛰기 = 굴림 × **`plotSkipSeenMul` 0.85**. 지붕을 보고 "어려우면 맡기고 쉬우면 쏜다"를 고르는 맛을 막는다.
    첫 살을 쏜 뒤에는 건너뛰기 단추가 없다 (쏘다 망치고 굴림으로 갈아타는 길 없음 — 그때는 「그만」= 조용히 물러남).
- 실측 (변한 판 · 고용 자객 · 가락 장수 · 시드 1000): 안 보고 맡김 **24.4%** · 본 뒤 맡김 **21.1%** (≈ ×0.85 — 같은 굴림이라 본 뒤 먹힌 판은 늘 안 보고도 먹힌 판).
- 손으로 쏘기는 빨간 바 위에서 각만 맞으면 맞는다 (`tools/probe-night.ts`, 빨간 바 계약) — 잘 쏘는 사람의 기대값이 굴림보다 높다. 건너뛰기는 "공정하되 조금 손해"로 둔다.
  사람이 쏜 먹힘 비율은 아직 실측이 없다 — 형의 판 기록(`hanbal.realm.games` 의 night 누름)이 쌓이면 0.85 를 다시 본다.
